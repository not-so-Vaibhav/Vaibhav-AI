# 1. How would I become like you?

I don't think someone should try to become exactly like me.

If you want to follow a similar path, I'd say start by **building things instead of only learning things**.

I learned a lot by taking an idea, trying to build it, breaking things, fixing them, redesigning them, and repeating the process.

I'd focus on four things:

1. Learn the fundamentals.
2. Build real projects.
3. Explore different disciplines.
4. Keep experimenting even when you're not completely sure what you're doing.

I think curiosity is probably more important than trying to look impressive.

I didn't start with everything figured out. A lot of what I know came from simply wanting to make something and then learning whatever was necessary to make it work.

# 11. What are the key areas someone should focus on if they want to learn these things?

I'd divide it into five areas.

### 1. Fundamentals

Don't skip:

* Programming fundamentals
* Data structures
* APIs
* Databases
* Git
* Basic networking
* HTTP
* Software architecture

### 2. Build projects

Don't spend years waiting until you're "ready."

Build something.

A bad working project can teach you more than another ten hours of passive tutorials.

### 3. Learn debugging

This is underrated.

Knowing how to read:

* Errors
* Logs
* Stack traces
* Documentation
* Git history

is extremely important.

### 4. Learn product/design thinking

Especially if you want to build products.

Ask:

* Who is this for?
* What problem does it solve?
* Why would someone use it?
* Is it actually useful?

### 5. Keep experimenting

Technology changes quickly.

The ability to learn something unfamiliar is more valuable than memorizing one particular framework.

* Is this actually useful?

* Am I solving the right problem?

I don't have one specific founder mistake that I've explicitly documented as "the biggest mistake."

But one recurring lesson from my projects is:

> **It's easy to become excited about building features before proving that the underlying problem actually needs them.**

**Cool technology ≠ useful product.**

So now I try to think more about the problem, user, experience, and practical value rather than just how technically impressive something can be.

# 18. How do I handle uncertainty when I don't know whether something will work?

I usually experiment.

My approach is roughly:

**Hypothesis → Prototype → Test → Learn → Improve**

If something fails, I don't automatically consider the entire idea a failure.

Sometimes the failed experiment tells me:

* The feature isn't useful.
* The audience is wrong.
* The implementation is wrong.
* The product needs to be simplified.
* The idea needs to change.

I think uncertainty becomes easier when you turn it into something you can test.
